## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
AC#1 benchmark (scripts/benchmark.py, 1,000,000 rows, 9 columns: integer, string, decimal(12,2), float decimal, enum, date, timestamp, boolean, nullable string; 84 MB csv). Machine: 4 cpus (nproc), x86_64 Linux VM, 15 GiB RAM, go1.24.9 linux/amd64, 2026-11-01. Peak RSS from os.wait4 rusage (no /usr/bin/time here).
- avro: 18.64s, 53,654 rows/s, peak RSS 20 MiB, output 65 MB
- parquet: 15.83s, 63,156 rows/s, peak RSS 36 MiB, output 55 MB
- 20k rows for comparison: avro RSS 19 MiB, parquet 24 MiB, so memory is flat in file size.
Profile (temporary go test with -cpuprofile on 300k rows, removed afterwards): the single parser goroutine is the bottleneck (~94% of wall time). In it: extract_args ~47% (regex FindStringSubmatch + a new map per cell), map copy/merge of args in parseValue ~25%, Convert ~25% (mostly decimal via big.Rat). ~23% of all CPU is mallocgc plus GC. Avro writer: one OCF block and one unbuffered write syscall per row; re-encoding 300k rows with fastavro's default blocks gives 14.3 MB vs 19.6 MB (+38% bloat). No regex recompilation per row (patterns compiled once in NewParser).
AC#2: tests/test_performance.py: 1M-row file with invalid ids at rows 3, 5, 7. Default flags exit non-zero in ~10 ms (bound 3s) with no output; --fail-fast=false --max-errors 3 likewise. For reference, --fail-fast=false without a limit on the same file reads to the end in ~18s. Whole module runs in <0.5s (file generated by repeating a 1000-row block).
AC#3 follow-ups: TASK-20 (reduce per-cell allocations in the parser), TASK-21 (write Avro output in multi-row blocks), TASK-22 (parse rows on multiple cores, depends on TASK-20). Nothing fixed directly.
